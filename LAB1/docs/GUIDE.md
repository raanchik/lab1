# Как устроено решение и почему

Документ нужен, чтобы ты понимал каждую часть кода и мог объяснить её на защите.
Решение следует контракту из ноутбука лекции: схема, коды ошибок, формат отчёта и
имена модулей взяты оттуда. Там, где я добавил своё, это помечено.

## 0. Что изменилось после ноутбука лекции

Первая версия проекта была написана до того, как появился ноутбук, и формат данных в ней
был придуман. Ноутбук — это и есть «памятка с общим контрактом» из задания, поэтому
проект переделан под него:

| Было (догадка) | Стало (контракт лекции) | Почему важно |
|---|---|---|
| декларация `used/description/tools` | `used/tool/purpose/verified_by_student` | иначе официальные файлы не пройдут валидацию |
| нет версии схемы | `schema_version` строго `int` = 1, иначе `unsupported_version` | эволюция формата без молчаливой смены смысла |
| коды `missing_field`, `invalid_type`… | `invalid_json`, `schema_error`, `unsupported_version`, `conflict` | единый словарь кодов курса |
| все ошибки записи сразу | первая найденная ошибка | так в лекции; проще контракт |
| пустая строка файла пропускалась | пустая строка = `invalid_json` | явная политика из лекции |
| повтор ключа JSON молча перезаписывался | повтор ключа и NaN отклоняются | строгий JSON |
| отчёт `score/similarity/evidence` | `report_id, submission_hash, config_hash, findings[], review_required` | отчёт привязан к версии сдачи и конфигурации |
| шаблон — отдельные строки | шаблон — блок подряд идущих строк | так в лекции |
| пустая декларация проверялась анализатором | неполная декларация отклоняется parser'ом | см. раздел 6 |
| пакет `school` | пакет `school_lab`, команда `school-lab` | структура из лекции |

## 1. В каком порядке читать код

`models.py` → `errors.py` → `parsing.py` → `hashing.py` → `repositories.py` →
`services.py` (приём и импорт) → `sources.py` → `analyzers.py` → `registry.py` →
`services.py` (анализ) → `app.py` → `cli.py`. Порядок совпадает с порядком разделов ноутбука.

## 2. Поток данных

```
файл.jsonl ─► JSONLSource.open()  ─► SourceRecord(line_no, raw | error=invalid_json)
                (владеет файлом)            │
                                            ▼
                         SubmissionService.accept(raw)
                           parse_submission  ─► schema_error / unsupported_version
                           submission_hash
                           repository.get    ─► duplicate / conflict
                           repository.add    ─► accepted
                                            │
                                            ▼
             AnalysisService.run(id, "template", context)
               registry.create ─► analyzer.analyze ─► AnalysisReport
               validate_report (граница)  ─► AnalysisFailure
```

## 3. Неделя 1: приём и валидация

### Почему валидация — явный код, а не аннотации (вопрос защиты №1)

**Type hint** проверяется mypy **до запуска** и только в нашем коде. Данные из файла
приходят **во время выполнения**: `json.loads` возвращает что угодно, и Python спокойно
положит число в переменную с аннотацией `str`. `TypedDict` тоже ничего не проверяет
при создании. **Parser** проверяет конкретные данные в рантайме, в том числе правила,
которые вообще не выражаются типом: «строка непустая», «есть часовой пояс»,
«нет лишних полей», «при used=true есть tool».

Три уровня дополняют друг друга: parser — данные, mypy — совместимость кода,
тесты — поведение на сценариях.

### Где выполняется валидация

В одном месте — `parsing.parse_submission`. Её вызывают `SubmissionService.accept`, тесты
и любой будущий адаптер. После неё в системе есть только корректные `Submission`.
Прямой вызов конструктора `Submission(...)` инварианты **не** проверяет — это граница,
которую нужно назвать на защите.

### Ловушки строгой проверки

- `bool` — подкласс `int`: `isinstance(True, int) is True`. Поэтому `schema_version`
  проверяется через `type(v) is int`, а `used` — через `type(v) is bool`.
- `bool("false") is True`: непустая строка истинна. Поэтому никаких `bool(value)` и `str(value)`.
- Отсутствующий ключ и `null` — разные состояния: сначала проверяется наличие поля, потом значение.
- Опечатка `studnet_id` даёт ошибку про отсутствующий `student_id`, а не пропадает молча.
- `strip()` только проверяет пустоту. В модель попадает **исходный** текст: на его строки
  ссылается evidence.

### Неизменяемость (вопрос защиты №2)

- `b = a` — не копия, а второе имя того же объекта.
- `dict.copy()` — **поверхностная** копия: внешний словарь новый, а вложенная
  `ai_declaration` общая. Изменение через копию видно в оригинале.
- `copy.deepcopy` копирует всё дерево. Это изолирует данные, но дорого и не заменяет
  продуманную модель.
- `@dataclass(frozen=True)` запрещает присваивание полей, но **тоже поверхностно**:
  список внутри frozen-объекта можно `append`. Поэтому в моделях нет списков, только
  строки, bool, вложенные frozen-модели и `tuple`.

Тест `test_schema_violations` после каждой ошибки сравнивает вход с копией, сделанной
до вызова: валидатор ничего не меняет даже при отказе.

### Хеш: почему SHA-256, а не hash()

Встроенный `hash()` для строк меняется между запусками Python (рандомизация), поэтому
идентификатором содержимого он быть не может. `stable_hash` — это SHA-256 от канонического
JSON (`sort_keys`, без пробелов, UTF-8, `allow_nan=False`). Порядок ключей на хеш
не влияет, а лишний `\n` в коде влияет. Хешируется вся сдача, поэтому одинаковый код двух
студентов — это разные хеши. SHA-256 не доказывает авторство и не является подписью.

### accepted / duplicate / conflict

`SubmissionService.accept`: сначала полная проверка, потом изменение состояния.
- нового id нет в хранилище → `add`, `accepted`;
- id есть, хеш тот же → `duplicate`, ничего не меняется;
- id есть, хеш другой → `SubmissionError("conflict")`, исходник не трогается.

Репозиторий дополнительно отказывается перезаписывать запись — это последняя линия обороны.
Новая версия работы — это новый `submission_id` (упражнение 2).

### Импорт с частичным успехом

`import_source` ловит **только** `SubmissionError`. Битая строка, ошибка схемы и
конфликт попадают в `errors` с `line_no`, импорт идёт дальше. Любое другое исключение —
это дефект кода, и он пролетает наружу (тест `test_unexpected_defect_is_not_swallowed`).
Атомарность — на уровне одной сдачи: принятое до ошибки остаётся.

`ImportSummary` использует `field(default_factory=list)`. Запись `errors: list = []`
дала бы всем отчётам один общий список (тест `test_import_summaries_do_not_share_lists`).

## 4. Неделя 2: источники и анализаторы

### Protocol и ABC (вопрос защиты №3)

- **ABC + наследование** — номинальная типизация: «ты анализатор, потому что объявил
  себя наследником». Уместно для общего базового поведения и управляемой иерархии.
- **Protocol** — структурная типизация: «ты анализатор, потому что у тебя есть нужные
  члены». Плагин не обязан импортировать наши базовые классы.

**Почему Protocol не заменяет контрактные тесты:** он проверяет только форму (имена
и сигнатуры), и только статически. Он не гарантирует, что файл закроется или что
evidence указывает на существующую строку. Это проверяют `validate_report` на каждом
вызове и контрактные тесты заранее.

### Генераторы и break (вопрос защиты №4)

Тело генератора начинает выполняться при первом `next()`, а не при создании.
После `break` генератор остаётся **приостановленным**: если бы файл открывался внутри
голого генератора, он закрылся бы только «когда-нибудь», когда сборщик мусора вызовет
`close()`. Это не гарантия.

Поэтому источник устроен так: `open()` — это контекстный менеджер (`@contextmanager`).
Внутри него `with handle:`, и уже потом `yield` итератора записей. Файлом владеет
**источник**, его жизнь ограничена блоком `with` у вызывающего. Выход из блока по
`break`, по исключению или по концу данных закрывает файл. Тесты проверяют это через
`last_closed`. Исключение при этом **не подавляется**: `@contextmanager` пробрасывает
его в точку `yield`, `finally` закрывает файл, ошибка летит дальше.

### Три источника, один контракт

`InMemorySource`, `JSONLSource` и `StreamSource` проходят одинаковые тесты: фикстура
`make_source` параметризована. In-memory выдаёт **копии**, поэтому потребитель не испортит
исходную коллекцию. `StreamSource` (упражнение 5) работает с уже открытым потоком и
**не закрывает его**: поток открыл вызывающий, он и закрывает. По ресурсному поведению
он не полностью эквивалентен JSONL, и это отличие записано в контракте и в тесте.

Ошибка **открытия** файла (`FileNotFoundError`) — это не ошибка записи: продолжать
нечего, поэтому CLI возвращает код 2, а не строку в `errors`.

### Отчёт и evidence

`AnalysisReport` связывает результат с конкретной версией сдачи (`submission_hash`),
анализатором (`analyzer_id`, `analyzer_version`) и конфигурацией (`config_hash`).
`report_id` идентифицирует **запуск**: у двух одинаковых анализов findings совпадают,
а report_id разный. `review_required` направляет работу человеку. Отчёт — это
наблюдение, а не вердикт.

`score` — конечное число от 0 до 1 либо `None` («метрика не определена»). `True`
отклоняется отдельно, иначе он стал бы оценкой 1 (упражнение 6).

### Почему LengthAnalyzer не оценивает качество (вопрос защиты №5)

Пятьдесят строк не гарантируют правильный алгоритм, а короткий код не означает
использования ИИ. Длина — это наблюдение без обоснованной связи с качеством, поэтому
`score=None`, а объяснение прямо говорит об ограничении. Evidence указывает на
непустые строки исходника. Соседние строки я склеиваю в диапазоны (`to_ranges`) — это моё
дополнение к лекции, контракт оно не нарушает.

### TemplateAnalyzer

Шаблон — **блок** подряд идущих строк, сравнение точное, без нормализации: пробел в конце
строки уже не совпадение. Пустой шаблон ничего не находит, иначе он «совпал бы» со всем.
Найденное помечается как разрешённое, а не как основание для санкций. Контекст чужого
задания даёт отказ (`context_mismatch`). Переименования и нечёткое сходство — тема ЛР 2.

### Реестр и центральный сервис

`AnalyzerRegistry` хранит `имя → фабрика`. `AnalysisService.run` спрашивает у реестра
анализатор по имени, и в нём **нет** ни одного `if name == "length"`. Новый анализатор
добавляется регистрацией. Реестр создаётся в точке сборки (`build_registry`, `app.py`),
каждый тест получает свой, глобального изменяемого состояния нет.

Реестр выбирает, но не гарантирует корректность. Поэтому проверяется:
пустое и повторное имя, неизвестное имя, совпадение имени с `analyzer_id`, и отчёт на границе.

Ловушка позднего связывания: `[lambda: name for name in names]` — все lambda вернут
последнее имя. Исправление: `lambda name=name: name` (тест `test_late_binding_pitfall`).

### Граница с кодом анализатора

`AnalysisService.run`:
1. сдача должна быть принята (`not_found`), контекст должен быть того же задания;
2. падение анализатора с любым исключением **явно преобразуется** в
   `AnalysisFailure(code="analyzer_crashed", field=<имя>)`, исходная причина остаётся
   в `__cause__` (`raise ... from exc`), а в журнал пишется traceback;
3. отчёт проверяется `validate_report` → `invalid_report`;
4. отчёт должен принадлежать вызванному анализатору (нельзя вернуть отчёт «от чужого имени»).

Здесь широкий `except Exception` уместен: это граница с чужим кодом и явное
преобразование, а не «глотание». Ошибка не исчезает, пользователь видит, какой
анализатор упал.

### Какие ошибки видит пользователь (вопрос защиты №6)

| Слой | Что | Как видит пользователь |
|---|---|---|
| источник | файла нет / не читается | stderr `{"code":"source_unavailable"}`, exit 2 |
| источник | битая строка | `errors[]`: `line_no`, `invalid_json` |
| домен | схема, версия, конфликт | `errors[]`: `line_no`, `code`, `field`, `message` |
| анализ | неизвестный анализатор, плагин | stderr, exit 2 (до начала работы) |
| анализ | падение/плохой отчёт | `analysis_errors[]`, exit 1 |
| интерфейс | неверные аргументы CLI | сообщение argparse, exit 2 |

Traceback пользователь видит только при настоящем дефекте кода.

## 5. Углубление Core

**Entry points.** В `pyproject.toml` плагина:
```toml
[project.entry-points."school_lab.analyzers"]
declaration = "school_lab_declaration:DeclarationAnalyzer"
```
После установки `registry.load_entry_points()` находит запись через
`importlib.metadata.entry_points`. Сразу при загрузке, а не при первом анализе,
проверяются: повтор имени, ошибка импорта (`plugin_error`), совпадение `entry.name`
с `analyzer_id`. Функцию поиска `discover` можно передать снаружи. Так тесты проверяют
все три сценария без установки пакетов. Папка на диске — **не** регистрация:
регистрирует только установка пакета. `entry.load()` исполняет код, поэтому механизм
годится только для доверенных расширений.

**Декоратор `@timed`.** Записан как `def timed[**P, R](...)` — это синтаксис Python 3.12
(PEP 695) для тех же `ParamSpec` P и `TypeVar` R; они сохраняют сигнатуру для mypy, `wraps`
сохраняет `__name__`, `__doc__`, `__wrapped__`. Время пишется в `finally`, то есть и при
исключении. Запись идёт в `logging`: пакет ставит только `NullHandler`, а уровень и
формат задаёт точка запуска.

**Метаклассы и дескрипторы** не добавлены: явный реестр проще, а сложный механизм
нужно оправдывать конкретным поведением. На защите можно показать, что `property` —
уже дескриптор (`type(Cls.__dict__["x"])` — это `property`).

## 6. Третий анализатор и почему parser уже требует tool/purpose

В PDF сказано: «третий анализатор проверяет наличие непустой AI-декларации при used=true».
В лекции parser уже отклоняет `used=true` без `tool` и `purpose`, то есть заведомо
неверная декларация не проходит границу приёма. `DeclarationAnalyzer` (в `examples/`):
- всё равно сам проверяет непустоту: `Submission` можно создать в обход parser, и
  анализатор не полагается слепо на чужую валидацию (тест `test_declaration_analyzer_checks_nonempty_itself`);
- описывает заявленное использование ИИ;
- ставит `review_required`, если ИИ использован, а студент не подтвердил проверку результата.

Он **не** определяет авторство: отсутствие заявления не доказывает, что ИИ не использовался.

## 7. Измерения (пример с машины разработки, Python 3.12, 3000 сдач)

| Метрика | Значение |
|---|---|
| Импорт (разбор + валидация + приём) | ~21 тыс. сдач/с |
| Один анализ (`run`) | ~100–110 мкс |
| Накладные расходы `@timed` | ~0,24 мкс/вызов, около 0,2% от анализа |
| `Submission` без slots / со slots | ~153 / ~112 байт на объект (без учёта строк полей) |

Что из этого следует:
- **Профиль** (`cProfile`): около 85% времени анализа — пересчёт SHA-256 через `asdict`.
  Отчёт проверяется дважды (в `make_report` и на границе сервиса), поэтому хеш сдачи и
  `config_hash` считаются по три раза за вызов. Сам подсчёт строк почти бесплатен.
  Оптимизация (кеш хеша) возможна, но не нужна: двойная проверка на границе — осознанное
  решение, а 0,1 мс — приемлемо.
- **Методика:** разница «с декоратором / без» на целом `run()` тонула в шуме ±5% и однажды
  вышла отрицательной. Поэтому накладные расходы измерены изолированно на пустой функции
  (`timeit`, минимум из повторов).
- **slots** экономит около 27% памяти на объект модели, но строки полей занимают больше,
  поэтому на общий расход памяти эффект невелик. Ускорения slots не гарантирует.

Запусти `python scripts/bench.py` у себя и вставь в отчёт **свои** числа.

## 8. Что требуется до production (вопрос защиты №7)

Постоянное хранилище и атомарная проверка конфликта (уникальное ограничение, транзакции);
ограничение размера входной строки; изоляция плагинов (сейчас они исполняются с правами
процесса); персистентный журнал и метрики; нечёткое сравнение кода; политика миграции
схемы v2; конкурентный доступ.

## 10. Сценарий защиты
